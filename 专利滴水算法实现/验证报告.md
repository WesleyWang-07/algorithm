## 二、为什么第二次切分（竖切）对不上

1. **大和七在真实图上是连成一体的**。连通分量分析显示：上、下各是一个整体墨块（上=1308px 单连通），并非分离的三块。视觉确认它上半是一根连贯的"匚框"横笔。
2. **因此没有一条能"笔直向下切分大/七"的竖直缝隙**。逐列空隙深度剖面显示，中部墨区（col6-122）几乎每一列的顶部竖直空隙只有 ~20-28px 就撞到墨（那根连通横笔）。真正的任意竖直滴从 col51-96 起，**全部在 (185,92) 右下角收尾**——它沿连通横笔的轮廓**横滑绕行**，而不是向下劈开。
3. 这正是论文 **§3.4.4 "字符笔画粘连情形"** 单独当作难点处理的工况：需要**熔断**在上部横笔的合适位置将其斩断、并配合精心选择的初始滴点。这一套调参在扫描版专利 + 论文 md 里**无法被完整还原**。

## 三、为什么"像素 IoU 校验"本身不可靠

- **红线压墨**：论文图里红线与墨迹重叠，我在剔除红线时把勾等部位的实际墨迹也擦掉了一块，导致"剔除红线后的图"与"未受干扰的真值部件"天然对不齐。
- **bbox 归一化失真**：把每个裁剪块压到 48×48 会抹掉纵横比信息，结果"上区（大+七，宽 116）"vs"大（宽 78）"归一化后形状差异被夸大。
- **部件未必与本图对应**：`p49_img1/2/3`（勾/大/七）与 img4 各区域的最佳 IoU 均在 0.1~0.3 之间（近乎噪声），说明这几张提取部件与本图的切分区不存在干净的一一对应。

## 四、真正可复现、可信的验证

真值线有 **19%~24% 的行踩在墨迹上**（面板A：125 行中 24 行；B：91 行中 17 行）。

#### 4.6 为什么本实现从 col 77 出发会滑走，而论文停在 77

`diag_topology.py` 打印核心区 ASCII 墨迹图（rows 15-95, cols 50-90）揭示：

```
row 20 ###########..............................
row 21 #######################..................   ← 横笔上缘（墨迹到 col 72）
row 22 #############################............
row 25 ##.......##############################..   ← 左端 col 50-58 已变白
row 28 #.............................###########   ← 墨迹已退到 col 79 之后
```

- **「大」的横笔是斜的**（左上→右下）。col=77 的第一段墨迹在 rows 22..27（厚 6），
  **row 21 的 col 77 是白的**，而右邻 (21,78) 也是白的 → 本实现判 `j=4, Q=4` → 滑走。
- col=77 全部墨迹段 = `(22,27)`, `(78,82)`, `(129,134)`；**穿越第一段后 rows 28..77
  有 50 行完全通畅**，再穿 5px 就能到 l1(row≈92)。**需熔断总厚度 = 11px。**

**到这里，一个自然的猜测是**：差距在"遇单侧开放时是否选择熔断穿越"——专利规则的
优先级是「滴落>飞溅>回流>熔断」，只要有一个正向邻点开着（哪怕只是侧向 j=4），
熔断永远排不上；而论文的 l₂ 显然在合适位置**选择了穿越**。

> ⚠️ **但这个猜测在 2026-09-17 三次复核中被否掉了**，见下方 4.7。原因是：
> "熔断"与"选优"是**两件独立的事**，而 4.6 只查了前者。

#### 4.7 **决定性反证：论文的 l₂ 不是"枚举 + 选优"能产生的**（2026-09-17 三次复核）

`diagnostics/diag_l2_selection.py` + `diag_l2_selection2.py` 两个判别实验。

**实验一：40 种 (δ₂ 带 × 指标 × tie-break) 组合，没有一种能选出 77。**

对 δ₂ 带的 5 种可能定义（`(2W/7,3W/5)`、按 `W-1` 算、`0.286..0.6`、`0.25..0.75`、
全宽）× 4 个指标（A/B/C/D）× 2 种 tie-break（严格小于 / 小于等于）= 40 种组合逐一枚举：

```
as-implemented (2W/7, 3W/5) | A | strict | -> c0=50
as-implemented (2W/7, 3W/5) | B | strict | -> c0=46     ← 当前实现的配置
as-implemented (2W/7, 3W/5) | C | strict | -> c0=44
as-implemented (2W/7, 3W/5) | D | strict | -> c0=44
wide (0.25..0.75)·W         | C | strict | -> c0=108
full width                  | A | strict | -> c0=1
...（共 40 行，无一行是 77）
```

**原因是结构性的，与参数无关**：δ₂ 带内所有起点只落在两个吸引子上——
`c0=8~27 → 终点 col 33`、`c0=28~49 → 终点 col 46`、`c0=50~110 → 终点 col 111`。
起点 77 属于最后一簇，它的终点是 **col 111**（不是真值 77），横向偏移 34 格；
而 42/46 那一簇偏移为 0~4 格。**77 在任何"越小越好"的指标下都排不进第一。**

**实验二：论文四面板"起点不同、路径相同"——本实现产生不了这种形状。**

论文图3-23 四面板实测三元组（起点列, 中间竖直段列, 终点列）：

| 面板 | 起点列 | 中间段列 | 终点列 |
|---|---|---|---|
| A | 57 | **63** | **77** |
| B | 77 | **63** | **77** |
| C | 63 | **63** | **77** |
| D | 63 | **63** | **77** |

**四面板起点各不相同，中间段与终点却完全一致。** 换指标只改"选哪个起点"，不改路径形状——
所以这四面板不可能是"同一算法跑四次"，更像是**同一条参考路径、四个不同起点的标注**。

而本实现在这张图上，各起点的**中间段列取值集合里根本没有 63**
（只有 `1~46` 与 `103~145` 两簇）：

```
起点 57 → 中间段 103，终点 111
起点 63 → 中间段 103，终点 111
起点 77 → 中间段 103，终点 111
```

**结论（推翻 4.6 的猜测）**：

> 差距**既不是"指标选择"、也不是"绕行方向"、也不是"是否熔断穿越"**，
> 而是**论文图3-23 的那条 l₂ 不是"改进滴水算法在 δ₂ 带内枚举选优"的产物**。
> 若目标线本身不是本算法能产生的，那么**无论怎么改规则、怎么调参数都到不了**。

这也解释了本报告一直记着的那句"未解之谜"：*论文 l₂ 起点列 57/77/63 与 δ₂ 枚举结果不一致*——
**它不是"风险"，而是该框架被证伪的反证。** 此前把它当风险记着，导致后两轮都在
"如何让 77 被选中/被走到"上打转，方向从一开始就错了。

**由此产生的项目定位修正**：

   而本项目实现的是**专利 2024 版改进滴水算法**，两者未必是同一个东西；
2. 本实现的正确性验证，应落在**能自洽检验的地方**：专利图4~图12 逐格校验（11/11 PASS）、
   400 组随机图有界性测试、合成谱字零熔断切分、MATLAB 独立实现逐位对照；
3. 「熔断改造」（此前记的"新方向③"）**失去依据**，不建议再做。
